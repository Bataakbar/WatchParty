Build a production-ready, desktop-first watch-party web application inspired by the concept of Rave.

## 1. CORE PRODUCT CONCEPT

The application is a synchronized watch-party platform.

The PRIMARY behavior is NOT screen sharing.

The PRIMARY behavior is:

1. A Host creates a watch room.
2. The system generates a short room code.
3. The Host opens a supported video page in the target website using their browser.
4. Guests join the room using the room code.
5. When the Host opens or changes to a supported video page, Guests automatically navigate to the same supported video page.
6. Each user's own browser loads and plays the video independently.
7. The application synchronizes playback state between Host and Guests.
8. The actual video/media data must NEVER pass through the application's backend.
9. Screen sharing must NOT be used for normal playback.
10. Screen sharing can exist only as an optional secondary feature in the future.

The intended experience is:

Host opens video
→ Guest automatically opens the same video
→ Guest loads the video locally
→ Host presses Play
→ Guest automatically plays
→ Host pauses
→ Guest pauses
→ Host seeks
→ Guest seeks
→ playback remains synchronized.

This is a WATCH-PARTY / SYNCHRONIZATION application, not a video streaming proxy.

---

# 2. SUPPORTED WEBSITE

The application should initially focus on ONE supported video website:

https://filmapik.college/

Do NOT build a generic "support every website" system.

Implement the website integration as a dedicated adapter so the architecture remains extensible.

Important:

* Do not download videos.
* Do not proxy video streams.
* Do not re-host video.
* Do not store copies of videos.
* Do not bypass DRM.
* Do not extract protected media URLs.
* Do not circumvent authentication or access controls.
* Do not redistribute video content through the application server.

The application should only synchronize the playback state of the user's own browser session.

Because third-party player behavior may vary, isolate all website-specific logic inside a dedicated browser-extension adapter.

# 9. JOIN FLOW

When a Guest joins:

1. Guest enters room code.
2. Frontend requests room information.
3. Frontend establishes WebSocket connection.
4. Server validates the room.
5. Server adds the participant.
6. Server sends current room state.
7. Browser extension is notified of the current media URL.
8. Extension opens the same supported URL.
9. Extension waits for the player to become ready.
10. Extension reports PLAYER_READY.
11. Server sends the authoritative playback state.
12. Guest seeks to the correct position.
13. Guest starts playing if the Host is currently playing.

The guest should NOT manually enter the video URL again.

# 12. PLAYBACK SYNCHRONIZATION

Do NOT send playback position continuously on every animation frame.

Use an event-driven synchronization system.

Immediately send:

* PLAY
* PAUSE
* SEEK
* RATE_CHANGE
* MEDIA_OPEN

Additionally send periodic synchronization snapshots every 2–5 seconds.

Example:

{
"type": "SYNC_STATE",
"position": 923.42,
"playing": true,
"rate": 1.0,
"timestamp": 1750000000000
}

The Guest calculates expected playback position based on the timestamp.

Example:

Host:
923.42

Guest:
923.21

Difference:
0.21 seconds

Do not perform a hard seek.

Instead, gently correct playback if possible.

Example:

Host:
923.42

Guest:
916.20

Difference:
7.22 seconds

Perform:

video.currentTime = authoritativePosition

Then resume playback.

# 13. CLOCK SYNCHRONIZATION

Implement a simple server-time synchronization mechanism.

The server provides an authoritative timestamp.

Clients estimate server clock offset during connection.

Use this offset when calculating playback position.

This reduces synchronization drift between clients.

# 17. WEBSITE NAVIGATION SYNCHRONIZATION

When Host navigates to a different supported movie page:

1. Extension detects URL change.
2. Extension identifies the media page.
3. Extension sends MEDIA_OPEN to FastAPI.
4. FastAPI updates room state.
5. FastAPI broadcasts MEDIA_OPEN to Guests.
6. Guest extensions receive the event.
7. Guest browsers navigate to the same supported URL.
8. Extensions wait for video player initialization.
9. Guests report PLAYER_READY.
10. Server sends the authoritative playback position.
11. Guests seek and play.

Expected behavior:

Host:
Open Movie A

Guests:
Automatically open Movie A

Host:
Play

Guests:
Automatically Play

Host:
Seek to 25:30

Guests:
Automatically seek to 25:30

# 18. MULTI-PLAYER / EXTERNAL PLAYER HANDLING

The supported site may contain multiple player containers, embedded iframes, or different player implementations.

Do not hardcode one fragile DOM selector throughout the entire application.

Create a dedicated player detection layer.

The adapter should attempt to:

1. detect the active player
2. determine whether it is an HTML5 video element
3. monitor player events
4. handle page navigation
5. handle player replacement
6. handle delayed player initialization

Gracefully display:

"Player not detected"

when a compatible player cannot be found.

Never attempt to bypass DRM or protected playback mechanisms.
